# Settl Plan 4, Slice 1 — iMessage Extension Foundation (design)

Date: 2026-06-26 · Status: approved design, pre-implementation

Parent spec: `2026-06-17-imessage-group-money-design.md` (the SwiftUI iMessage extension, deferred to "Plan 4" there and in earlier plan scope docs). Backend Plans 1–3 are complete and merged.

---

## What this is

Plan 4 is the SwiftUI iMessage extension — the whole client surface. It is too large for one spec, so it is decomposed into vertical tracer-bullet slices, each its own spec → plan → build cycle:

1. **Foundation** (this slice): Xcode project, a testable Swift API client, device-id, claim flow, read-only balances view.
2. Create-split + the `MSMessage` card bubble (and in-app group creation + real token discovery).
3. Settle: Venmo deep-link + record + creditor confirm + manual mark.
4. Pool (progress), order (by-item), loan create flows.
5. Chase: drafted reminder inserting the Plan 3 web settle link.

This slice is the tracer bullet: it proves the full stack — iMessage extension → HTTP API → ledger — works on-device before any feature is built on it. Success = open the extension in a Messages conversation, connect to a group, tap "I'm Jake," and see netted balances.

## Why a tracer bullet first

The riskiest unknowns are the iMessage-specific plumbing and the extension↔backend contract, not the ledger (already proven). This slice de-risks: an `MSMessagesAppExtension` built via XcodeGen launching in the simulator and hosting SwiftUI; HTTPS calls to the Supabase edge function round-tripping our Codable models; and the claim→balances ledger interaction on-device.

## Project layout & targets

New `ios/` directory, managed by **XcodeGen** (installed): a declarative `project.yml` is the committed source of truth; the generated `.xcodeproj` is git-ignored. This keeps the project diffable and agent-editable instead of a hand-rolled, merge-hostile `.pbxproj`.

```
ios/
  project.yml              # committed — source of truth
  Settl.xcodeproj/         # generated by xcodegen, git-ignored
  Settl/                   # host app target (minimal SwiftUI shell, no push)
  SettlMessages/           # iMessage app extension target (MSMessagesAppExtension)
  SettlKit/                # local Swift package — the testable, UI-free core
```

- **Host app `Settl`**: a single SwiftUI screen telling the user to open Settl inside a Messages conversation. It exists so the App Store bundle has something to list; it does not register for push (per the parent spec's extension-only decision).
- **Extension `SettlMessages`**: principal class `MessagesViewController: MSMessagesAppViewController`, which hosts a SwiftUI root view through a `UIHostingController`.
- **`SettlKit`** (local SwiftPM package, **Foundation only — no UIKit, Messages, or SwiftUI imports**): so `cd ios/SettlKit && swift test` runs the real logic tests headlessly without Xcode or a simulator. All Messages/SwiftUI code lives in the app and extension targets; all testable logic lives here.

## The testable core — `SettlKit`

Each unit is independently testable:

- **Models**: `Codable` structs matching the API JSON for this slice — a `Transfer { fromMemberId, toMemberId, amountCents }`, a member row `{ id, displayName, claimed }`, and the claim request body. Field names map to the API's camelCase JSON.
- **APIClient**: `async` methods over `URLSession`, sending `x-settl-token` (group invite token) and `x-settl-device` (device id) headers, for exactly the three calls this slice makes: list members, get balances, claim. Maps non-2xx responses to typed errors (unauthorized, conflict, other).
- **DeviceID**: generates a per-install UUID on first use and persists it (UserDefaults via an injectable store, so it is testable). This is the spec's "device-generated ID," distinct from Apple's per-conversation participant identifier.
- **Config**: the API base URL (this slice points at the local `supabase functions serve` endpoint, which the simulator can reach at `127.0.0.1`) and header names.

## Backend prerequisite (the only backend change)

The claim UI must list the named seats, but the backend today exposes only `POST /groups/:id/members`, no read. So this slice begins with one backend addition, built and tested with deno the same way as all prior backend work:

- **`GET /groups/:id/members` → `[{ id, displayName, claimed }]`**, group-token-gated (via the existing `authorizeGroup`). A `listMembers(db, groupId)` in `repo.ts` and a route branch in `router.ts`. It returns member identity and claimed status only — not device ids or settle tokens.

## Slice 1 UX flow

1. Open the extension in a chat. The SwiftUI root checks for a stored connection (groupId + invite token). None on first use.
2. **ConnectView**: the user pastes a `groupId` and `inviteToken`. (The implementation plan includes `curl` commands to seed a group with members A/B/C against the local API and print those values, so the manual verification is reproducible. This is an explicit dev scaffold.)
3. **GroupView**: loads `GET /groups/:id/members` and `GET /groups/:id/balances`, renders the member seats (with claimed/unclaimed state) and the netted balances.
4. Tap **"I'm Jake"** → `POST /groups/:id/claim` `{ memberId }` with the persisted device id in `x-settl-device` and the invite token in `x-settl-token`. On success the seat is bound to this device; the view refreshes.

**Deliberately deferred to Slice 2:** in-app group *creation*, and the `MSMessage` card bubble that carries `(groupId, inviteToken)` between participants in a conversation (real token discovery). Slice 1 connects to a pre-seeded group by pasted token.

## Error handling

- Network failure → inline error state with a retry affordance; no optimistic UI (the parent spec's "never optimistic about money").
- Bad/missing token (401/403) → "couldn't connect to this group."
- Claim hijack (409, seat already claimed by another device) → "already claimed."
- The extension shows pending/loading state until the backend confirms each read or write.

## Testing / verification

Per the agreed working model (headless coverage by the agent; final manual check by the user):

- **Backend `GET /members`**: deno tests, real red-green, same harness as Plans 1–3 (local Supabase + service-role key).
- **SettlKit (XCTest, headless via `swift test`)**:
  - Models decode against **real captured API JSON** — fixtures curled from the running edge function, never hand-invented (parent Rule 5).
  - APIClient tested via a `URLProtocol` stub: correct method/path/headers sent, success and each error mapping. The stub replays captured responses.
  - DeviceID: first call generates and persists; subsequent calls return the same id; uses an injected in-memory store.
- **Build**: `xcodebuild` compiles the host app and the extension for an iOS 26 simulator (compile-verified, not just `swift build`).
- **Manual (user, ~2 min)**: run the `SettlMessages` scheme in the Messages simulator, connect to the seeded group, tap "I'm Jake," confirm the balances render. This is the part the agentic loop cannot prove.

## Explicitly out of scope (later slices / not this slice)

- In-app group creation and the `MSMessage` card bubble + token discovery — Slice 2.
- Any create flow (split/order/loan/pool), settle, Venmo deep-link, manual mark — Slices 2–4.
- Chase / drafted reminders — Slice 5.
- Deploying the edge function for real-device (non-simulator) use — revisited when a slice needs device testing; this slice is simulator + local Supabase.
- Push notifications / companion app — out of v1 entirely per the parent spec.
