# Settl Plan 3 — Web Settle Page (design)

Date: 2026-06-25 · Status: approved design, pre-implementation

Supersedes nothing; extends the Plan 1 (ledger-core) + Plan 2 (api-and-flows) backend. Parent spec: `2026-06-17-imessage-group-money-design.md` (the web settle page is deferred to "Plan 3" there and in the Plan 2 scope doc).

---

## What this is

A no-install web page a debtor opens from the chase reminder link. It shows *"You owe Charlie $14"* and a *[Pay with Venmo]* button. It is **read-only**: it displays a member's netted balance and offers a Venmo pay link. It does not write to the ledger.

The page is served by the existing `api` Supabase edge function as server-rendered HTML. There is no second host and no client-side JavaScript.

## Why read-only (the load-bearing scope decision)

Plan 2's final hardening established: a settlement may only be written by a real party, proven by their bound device. `recordSettlement` requires the caller's device to be a *claimed* debtor or creditor; `confirmSettlement` requires the creditor's bound device. The guarantee is *a non-party cannot create or erase a debt*.

The web debtor has nothing installed — no claimed seat, no bound device, only the settle link. The link is a forwardable, screenshottable secret (that is why §"The link" scopes it tightly). If holding the link were enough to write settlement rows, anyone who saw the link could mark debts paid that were not, silently changing the ledger — reopening exactly the non-party-write hole Plan 2 closed, on the least-trusted surface in the system.

So the web page stops at "pay in Venmo." Recording stays where it is hardened: the creditor, who has the app and a bound device, confirms receipt through the existing `confirmSettlement` path (or marks manually). Nothing is lost — the debt still settles correctly; the trusted device-holder records it, not the untrusted public link. This fits v1's model: there is no push or companion, so the creditor learns of the payment by opening the chat anyway, and the parent spec already says "the creditor can always mark manually."

Option B (web "I paid" pre-creates a `proposed` settlement) is explicitly deferred. It saves the creditor one tap at the cost of a token-only write path that a leaked link could spam; not worth it while no push exists to notify the creditor.

## Data model change

One migration adds a per-member settle token:

- **members** gains `settle_token text not null default <random-secret>`, generated by the same mechanism `groups.invite_token` uses. It is minted automatically on insert, so `addMembers` needs no code change.

The token is per-member and read-only. Its leak blast radius is one member's net balance plus a Venmo pay button — nothing writable, no group-wide power. This is deliberately a *different* credential from `groups.invite_token` (which grants full create/read/settle and is the join secret for installed members). Revoking a settle link = rotating that member's column.

## The link and authorization

```
GET /settle/:groupId/:memberId?t=<settleToken>
```

A new `authorizeSettleToken(db, groupId, memberId, token)` helper matches `(group_id, id, settle_token)` against the `members` table. It is separate from `authorizeGroup` — a distinct, read-only credential. On mismatch or missing token it signals "not a valid link."

## What the page shows

Resolve the group's netted transfers with the existing `getNettedTransfers(groupId)`, then select the transfers whose `fromMemberId` is this member:

- **Owes someone** → *"You owe {creditorName} ${amount}"* + a `[Pay with Venmo]` button. Netting can split one debtor across more than one creditor; render one line + button per creditor (rare, but correct).
- **Owes nothing / is a net creditor** → *"You're all settled up"*, no button.
- **Creditor has no Venmo handle** → show the amount and *"{creditorName} hasn't added a Venmo handle yet"* instead of a broken button.

Member display names and the creditor's `venmo_handle` come from the `members` rows. All interpolated values are HTML-escaped.

## Venmo link

A pure function in `_shared/`:

```
buildVenmoPayLink({ handle, amountCents, note }) -> string
```

Returns the escaped `https://venmo.com/...` universal pay link (opens the Venmo app if installed, else browser/app-store — per the parent spec's "No Venmo installed" edge case). The debtor pays the creditor, so the intent is `txn=pay` to the creditor's handle, amount in dollars, with a note such as *"Settling up via Settl"*.

The exact query-param spelling is verified against Venmo's live link docs immediately before the builder is written — not from memory. The unit test asserts against that verified format.

## Rendering

A pure `renderSettlePage(view)` returns a self-contained HTML string: inline `<style>`, mobile-viewport meta, no external assets, no client JS. The route returns it with `content-type: text/html`. `view` is a small plain object (member name, a list of `{ creditorName, amountCents, payLink | null }`, settled-up flag) so the renderer is testable without a database.

## Error handling

The settle route returns **HTML**, not JSON, because a human reads it:

- Bad or missing token, unknown group/member → `404 text/html` with a short "this link isn't valid" page.
- Unexpected server error → `500 text/html` with a short generic message.

The existing JSON routes in the router are unchanged; only the settle route branch produces HTML.

## Testing (intent, not just behavior)

- **`buildVenmoPayLink`** — asserts the verified `https://venmo.com` format and correct escaping of special characters in the note and handle. A wrong/unescaped URL = a broken or wrong-amount payment, so this guards real money.
- **`renderSettlePage`** — pure: owes-one-creditor, owes-multiple, settled-up, and missing-handle views each render the right text and the right (or absent) button. HTML-escaping of a hostile display name is asserted.
- **Settle route (integration, local Supabase, same style as `api_test.ts`)** — seed group/members/event, then GET the route:
  - correct owed amount and creditor handle appear in the HTML;
  - settled-up member shows no button;
  - bad token → 404;
  - creditor-without-handle case shows the fallback, not a button.

## Explicitly out of scope (later plans / not v1)

- **Web-initiated settlement recording** (option B above) — deferred; recording stays device-gated in the extension.
- **Pool progress visualization** on the web page — Plan 4 territory.
- **SwiftUI iMessage extension** and the chase-reminder UI that *generates* the link — Plan 4. (Plan 3 builds the page the link points to; the extension that inserts the link is later.)
- **Rate limiting / abuse protection** beyond the per-member token — revisit before public exposure.
